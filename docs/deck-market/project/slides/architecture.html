TARGET ARCHITECTURE

Copies scale the stateless steps; one writer per partition keeps order

Stage A (identity, Jev gate, embed) depends only on the complaint itself, so we add copies until throughput is met.

Stage B (match, verify, LLM, new issues) runs one writer per business × area, so each partition stays in order while partitions run side by side.

Projected design; today’s prototype runs as one process. 7 partitions for grocery, about 700 for 100 businesses.

Here is the target design. Complaints arrive from four channels into a stateless intake API and a queue. Stage A workers resolve the customer, run the Jev gate and embed the text. None of that needs shared state, so we just add copies. Their output goes onto a queue keyed by business and area. Stage B is where order matters, because the list of known issues grows as new problems are discovered. So each business-and-area partition gets exactly one writer. A grocery business has 7 partitions; 100 businesses have about 700, all running in parallel. Results land in Postgres with pgvector, and the Curator, the ranker and the dashboard read from there.
